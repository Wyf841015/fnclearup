# 【fnOS 应用发布】清理精灵 —— 应用卸载了，目录清干净了，账号还留着（v0.13.0）

> fnOS 上的清理工具。这版加的是「用户清理」：把卸载应用后留下的系统账号列出来，你勾、你确认，它才删。

【截图 1：清理回收 → 用户 面板】

## 为什么加这个

fnOS 每装一个应用，系统里就多一个同名账号，gid 固定 901。应用中心点卸载，应用目录、`@appdata` 会一起收走，但**账号常常留在 `/etc/passwd` 里**。装过、卸过几十次之后，这些账号就攒成一堆没人认识的名字。

以前清理精灵只管目录和文件，账户这块是空的。加这个功能那天我在自己机器上看了一眼：

```
账号 95 个：系统 43、应用 51、真实用户 1
其中只有 35 个能删
```

`EmbyServer` 这种就是典型——早先装过一版 Emby，后来换了个账号重装，老账号一直挂着，家目录 `/home/EmbyServer` 里的东西也还在。目录清理能扫到它，但账户本身扫不掉。

## 界面就一张表

顶部四张卡：总账号数、应用账号、系统账号、可删除。

下面一行一个账号：用户名、UID、GID、类型（应用 / 真实用户 / 系统）、家目录、说明。

**默认不显示系统自带账号**（uid 小于 900 的那批：root、daemon、package、polkitd、各种 nodejs/python 运行时账号）。这个开关记在浏览器本地，勾一次就一直开着，但刷新回来默认还是隐藏——毕竟绝大多数人不需要看这 43 行。

能删的行正常显示，勾选框可用，说明列写「可删除」。

不能删的行**整行变灰、勾选框直接禁用、说明列写原因**。比如：

- `应用「fnclearup」仍在安装中，请先在应用中心卸载`
- `仍有 3 个进程在运行`
- `系统/服务账号（uid 7 < 900），不可删除`

这条是我特意改的设计：不要让人勾上一堆、点删除、等转圈、然后弹一句「删除失败」。该拦的在列表里就说清楚。

【截图 2：勾选几个残留账号，不可删的已标灰】

## 删之前要过三道

点「删除选中」弹出来的确认框里：

1. **列清楚要删谁** —— 用户名、uid、家目录，一行一个，不是一句"确定删除吗"
2. **「同时删除家目录」（`userdel -r`）默认不勾** —— 账户和家目录里的文件是两件事，默认只删账户。真要把家目录一起清掉，得自己勾
3. **必须勾「我确认删除这些账号」**，右下角「确认删除」才会从灰变红

如果选中的账号里有家目录不允许删的（家目录是 `/`、`/root`、`/home`、`/usr`，或者是卷根 `/vol1` 这种），第 2 条直接变灰不让勾。

## 判据在服务端，前端标灰只是提前告诉你

真正的拦截在 `POST /api/users/delete` 里，服务端会把每个账号重新过一遍：

| 情况 | 结果 |
|---|---|
| root、admin、package、polkitd 等核心账号 | 拒绝 |
| uid < 900 系统自带 | 拒绝 |
| 应用仍在安装中（`appcenter-cli list` 拿列表，`id -u` 对 uid） | 拒绝 |
| 有进程在跑（一次 `ps -eo uid=` 统计） | 拒绝 |
| 应用账号但 gid 不是 901 | 拒绝 |
| 家目录是 `/`、`/root`、`/home`、`/usr`、卷根 | 只删账号，不动文件 |
| 目录还属于这个账号（扫 `@app*`） | 只提示，不阻止 |

最后一条得解释一下：目录还在**不拦**。残留账号之所以要清，往往就是因为它对应的目录已经被清掉了——要是因为"还有目录"就不让删，这功能等于没有。这里只把目录路径当提示写出来，让你知道删完之后还能不能顺手把目录带走。

另外：一次最多 20 个。选多了前端会自己分批提交（20 / 20 / 5 这样），最后汇总一条结果。

## 一个把我自己坑到的 bug

用户清理推上去不到半小时，反馈回来：**全选之后点删除，提示「已删除 0 个账号」**。

两个原因叠在一起：

第一个，我在后端留了单次 20 个的上限。全选 35 个，第一次请求就超了，后端老老实实回 400「一次最多删除 20 个用户」。

第二个才是真正恶心的。前端封装的 `API.post` 在 `parseFetchResponse` 里对 4xx **不抛异常**，只给返回体挂一个 `__ok = false`。我的删除函数直接读 `d.deleted` —— 因为是 400，返回体里没这个字段，`undefined.length` 变空数组，界面上就成了「已删除 0 个账号」。

后端明明把原因写在 `error` 里了，前端看都没看。用户看到的现象是"点了删除，一个都没删"，真实原因是"一次最多 20 个"，中间隔着两层静默。

修法不复杂：校验 `__ok` 和 `success`，失败就把 `error` 原样弹出来；超过 20 个自己分批。现在选 45 个会发三次请求（20 / 20 / 5），提示「已删除 45 个账号」。

写测试的时候，这四件事都变成断言了：分三批、每批不超过 20、批量结果汇总、后端拒绝时提示里必须包含真实原因并且不能出现"已删除 0 个"。

## 顺手改的：首页那个弹窗

每次进应用都先弹一次风险提示，看过 20 遍之后就是纯打扰。这版在弹窗里加了勾选框「每次进入应用都弹出这个提示」，取消勾选就不再自动弹。「系统清理」页里有同一个开关，两处状态同步。

同步这里我没用 `document.activeElement` 判断用户点的是哪一个——fnOS 的 WebView 里焦点经常不在你以为的地方。改成比对"谁的 checked 跟存储里的旧值不一样"，谁变了就是谁被点的。

## 测试是怎么做的

`node --test tests/*.js` → 515 passed / 0 failed，其中用户清理 24 个。

难点是删除这事在本机没法真测。跑测试的是普通用户，既不能建账号，也不能删账号。

所以后端那 13 个用例全部跑在夹具上：`TRM_PASSWD_FILE` 指向一个假的 `/etc/passwd`，`PATH` 前面挂三个 mock —— `userdel`（只把参数写进日志，不真删）、`appcenter-cli`（假装某个应用还在安装）、`id`（配合上一条给出 uid）。于是一条完整的删除路径能真跑起来，还能断言 `userdel` 到底有没有带 `-r`。

前端 11 个用例用 happy-dom 真跑：渲染、全选只勾可删的、弹窗门闩、超过 20 自动分批、错误透出。

线上验证只做了不碰数据的部分：拉列表、21 个**不存在**的假账号 POST 回去看是否 400。你自己的账号一个都没动过。

## 已知的边界

- 只处理 Linux 系统账号，不碰 fnOS「用户管理」里的成员、权限、共享设置
- gid 不是 901 的账号不给删。这类账号不是应用中心建的，可能是别的东西在用，删了出事不好查
- 家目录不在常规位置的（比如直接在卷根下），只删账号，不动文件
- 删完账号之后，它名下的目录/文件还在磁盘上，需要回到「应用」或「网盘」面板去清目录

## 适合谁 / 不适合谁

✅ 适合：反复装卸应用、`/etc/passwd` 里攒了一堆不认识名字、或者从别处接手的机器

❌ 不适合：想通过它管理 fnOS 用户（成员、密码、共享目录）的。这里只做清理，不做用户管理，那活归系统设置
